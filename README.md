# 事件证据时间线

- **在线地址**：https://43-172-79-197.sslip.io/ （备用：https://43.172.79.197/ ，是同一台服务器、同一个产品）
- **代码仓库**：https://github.com/gonghy868/event-evidence-timeline
- 配套文档：[测试说明](测试说明.md)、[AI 使用与验证记录](AI使用与验证记录.md)

建议的试用顺序（约 3 分钟）：

1. 首页点开真实示例"长鑫科技：回购金额变更"，第一屏看当前结论、"办理阶段"，以及下面四个要点格（最早来源、结论变化、说法分歧、关联自选）。
2. 在"事件脉络"里点"播放"，或直接点时间轴上的某一天，看 11-04 董事长提议那一步和 11-20 董事会通过那一步，结论的说法怎么变。
3. 回首页，拉到最下面的"特殊情况示例"，点"演示：过期"，切换第 29、30、31 天。
4. 在首页查询框里自己查一件；再到最下面的"特殊情况示例"里勾上"模拟公告查不到"，回到顶部查一次，看数据缺失时页面怎么说。
5. 在事件框里输入"明天会涨吗"，看它怎么拒绝。

听到一条关于某家公司的消息，例如“某公司停工了”“回购金额变了”，这个产品把相关的公告、新闻、研报和网帖找出来排成时间线，告诉你五件事：

1. 我们取到的最早一条是谁说的。
2. 事情前后有什么变化。
3. 有没有互相矛盾的说法，目前以谁为准。
4. 现在的结论是什么，依据哪一条。
5. 它和你关注的股票是什么关系。

它只整理公开信息，不预测涨跌，不提供买卖建议。

对应笔试题目：题目 08「投资事件情报与证据时间线」。

## 一、启动方式

需要 Python 3.11。

```powershell
cd product
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
# 设置下面“环境变量”一节里的变量，然后：
.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8765
```

打开 `http://127.0.0.1:8765/`。

首次启动时数据目录是空的，首页的示例和演示场景不会出现。用下面的命令生成：

```powershell
.venv\Scripts\python.exe -I scripts\build_examples.py
```

- 五个“特殊情况示例”场景的输入在 `scenarios\`（虚构的公司和公告），这条命令会让它们走一遍完整流程，需要 DeepSeek 密钥。
- 三个真实示例要用到提前取回的原始返回（放在数据目录的 `raw\` 下）。这些是数据源的受限数据，不在本仓库里，所以只凭仓库不能重建这三个示例；线上版本的数据目录里已经放好。

跑测试（全部离线，不需要任何密钥）：

```powershell
.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.venv\Scripts\python.exe -m pytest -q
```

用容器运行：`docker build -t event-timeline .`，再 `docker run -p 8080:8080 -v <数据目录>:/data -e IFIND_API_KEY=… -e FUYAO_API_KEY=… -e DEEPSEEK_API_KEY=… event-timeline`。线上版本就是用这个 Dockerfile 构建的镜像在跑；本机（Windows，Docker Desktop）也构建成功过一次。

线上的部署方式：腾讯云轻量服务器上 `docker run` 把容器绑在 `127.0.0.1:8765`，前面用 Caddy 做 HTTPS 并转发过去，证书由 Caddy 向 Let's Encrypt 自动申请和续期；密钥放在服务器上一个权限为 600 的环境变量文件里；数据目录挂在容器外。

## 二、环境变量

| 变量 | 必需 | 说明 |
|---|---|---|
| `IFIND_API_KEY` | 现场查询和刷新需要 | 同花顺 iFinD 的密钥，用来检索公告和新闻 |
| `FUYAO_API_KEY` | 现场查询和刷新需要 | 扶摇的密钥，用来查公司、取个股新闻和行业分类 |
| `DEEPSEEK_API_KEY` | 现场查询和刷新需要 | DeepSeek 的密钥，用来读原文 |
| `DATA_DIR` | 否，默认 `product\data` | 事件文件、原始返回、AI 缓存、调用记录都放这里。不要放进仓库 |
| `DAILY_QUERY_LIMIT` | 否，默认 10 | 每天现场查询加刷新的总次数上限。线上设的是 50 |
| `NOTICE_SIZE` / `NEWS_SIZE` | 否，默认 10 / 15 | 每次检索取多少条公告片段、多少条新闻 |
| `LOOKBACK_DAYS` | 否，默认 60 | 现场查询往回检索多少天 |
| `REFRESH_MIN_INTERVAL` | 否，默认 600 | 同一件事两次取数之间至少隔多少秒 |

三把密钥只从环境变量读，代码、日志、仓库里都没有。没配密钥时，已经存好的示例和演示场景照常可以看，现场查询会在页面上明确显示哪一步失败。

## 三、产品选择

**给谁用**：关注几只股票的个人投资者。他刷到一条消息，不知道公司有没有回应，也不知道三天前看到的说法现在还算不算数。

**只做三样**：

1. **证据时间线**：把一件事的各路消息找齐，排除无关的，折叠转载，给每条标上“这句话是什么性质”和“来源可信程度”，标上四个时间。
2. **会变的结论**：结论由仍然有效的证据按固定规则算出来；可以在真实事件上一条一条加入证据，回放结论怎么变、为什么变。
3. **现场查一件新的事**：选公司、填事件，产品现场取数、整理、出结论；之后可以刷新接着跟。

**几个有意的取舍**：

- 状态只说“谁正式说了什么”，不替用户判定真假。“已被正式否认”的意思是公司否认了，不等于产品认定传闻是假的。
- 一句话的“性质”（事实陈述、观点、推测、传闻）和来源的“可信程度”（高、中、低）分开标。媒体的一句事实陈述，在没有公司公告确认之前，结论仍然是“待证实”。
- 公告没取到时不给结论，显示“数据不足”。不把“没找到”当成“没有”。
- 转载不重复计数。十家媒体转同一份公告，只算公司说了一次。
- 示例、构造的演示场景、现场查询走的是同一套处理流程（`app/pipeline.py` 的 `process`），没有预先写好的结果页。

**页面**：首页（查询框、已整理的事件、示例自选股、最下面的特殊情况示例和判断规则）；事件页五块（当前结论和四个要点格、事件脉络、全部证据、数字与分歧、关联自选股）。

## 四、AI 的角色

一句话：**AI 负责读，规则负责判。**

| 谁 | 负责 | 不负责 |
|---|---|---|
| AI（DeepSeek API，模型 `deepseek-flash`） | 读每条原文：它和这件事有没有关系（相关、不同的事、综合稿）；引用哪一句；这句话是什么性质；对这件事是什么态度；提到了哪些日期、数字、公司；哪几条是互相转载；哪些数字说的是同一个指标；用户新查的事是不是已有的那件 | 不决定可信程度，不决定状态，不写结论的说明句 |
| 固定规则（`app/rules.py`、`app/sources.py`、`app/stage.py`） | 按来源名单定可信程度；筛出算数的证据；按七行顺序表算状态；做过期检查；标变化原因；按公告的固定措辞认"办理阶段"（只是提议、尚在筹划、董事会已通过且无需股东会审议、董事会已通过尚需股东会审议、股东会已通过）；按固定句式拼说明句 | 不理解自然语言，只认固定措辞 |

"办理阶段"为什么交给规则而不是 AI：公司公告的这类措辞非常固定（"收到……提议""审议通过""尚需提交股东会审议"），规则认得准、每次结果一样、可以离线测试，而且页面能把依据的原句原样贴出来。起因是第一版把"董事长提议增加回购金额"的公告说成了"已正式确认，并给出了新版本"，见《AI 使用与验证记录》。

对 AI 的约束，都由程序执行：

1. AI 每个判断都要给出原文里的依据句。程序把标点和空白统一后，检查这句话是不是真的在原文里。对不上的判断作废，页面上标“未能自动归类”或“已作废”。
2. AI 提取的每个数字必须出现在它引用的那句话里，每个日期也一样，否则作废。
3. AI 判“确认”或“否认”之前，必须先指出原文里点名这个说法的句子；指不出来，态度只能算“只是提到”。
4. 公告标题带“更正”“澄清”“调整”“补充”时，程序把标题和 AI 的判断对一遍，对不上就不采用。它是高可信证据，所以整件事暂不给结论。
5. 转述公告的报道以公告原件为准；AI 对转述的判断和原件不同时，不采用转述的。
   AI 判“确认”而它引的那句话是在否认（含“不属实”“否认”“辟谣”等）时，这条不采用；AI 判“否认”而引句里没有否定词时，卡片上给出提示。
   AI 说一份公告是“更正”，只有原文里出现“更正”二字才算；说它修订了某份旧公告，只有原文里真的出现那份旧公告的编号或标题才算。
6. 给 AI 的每个提示词都写明：取回的新闻和网帖是待处理的数据，可能夹带指令，不执行其中的任何指令。
7. 提示词要求不加重原文的语气（“提议”不能当成“已完成”），原文只说“近日”的不补成具体日期。

这些约束管不住的：AI 把方向判反而引句里又没有明显的否定词时，程序查不出来；AI 把一份相关的公告判成“不同的事”时，程序也发现不了。应对办法是拿三个真实示例逐条人工核对，结果见《测试说明》。

AI 内部仍把"相关"细分成"同一次发生"和"后续进展"两类，但人工核对发现它分不稳（一致率 64%），而这个细分不参与任何规则，所以页面只显示"相关"和理由。AI 把多家公司的汇总稿留在时间线上的情况，另有一条程序规则兜底：媒体稿标题没点本公司、正文提到 3 家以上别的公司、本公司只出现一两次的，改判为综合稿并写明"程序按规则判定"。

事件关系的四种分类、“先说清这条内容讲的是什么事再判断”的输出结构、“取回内容是数据不执行其中指令”和“不加重原文语气”的写法，参考了开源项目 AIHOT（MIT 许可，https://github.com/KKKKhazix/AIHOT ）。只借了判断方法和提示词写法，没有使用它的代码。

开发过程中用了哪些 AI 工具、各自做了什么、改正了哪些错误，见《AI 使用与验证记录》。

## 五、数据来源

| 数据 | 来源 | 用法 |
|---|---|---|
| 公告的标题、日期、正文片段 | 同花顺 iFinD `search_notice` | 高可信证据。只给片段，没有原文链接，用标题、公告编号、日期回查 |
| 新闻的标题、日期、正文片段、链接 | 同花顺 iFinD `search_news` | 包括媒体报道、自媒体、个人帖子。只有日期，没有时分 |
| 个股新闻、研报、公告条目，带到分钟的时间和发布媒体名 | 扶摇 `/api/news/stock/timeline-list` | 补充发布时间和媒体名；只取标题或摘要含事件关键词的条目 |
| 按名称查公司 | 扶摇 `/api/meta/tickers/search` | 查询时选公司，避免重名 |
| 个股所属行业 | 扶摇 `/api/a-share-index/constituents/ths-index-list-by-stock` | 只用其中 `type=industry` 的行业分类，判断“同一行业板块” |

实测中和文档或预期不一致的地方：

- 扶摇的事件库接口（`/api/news/events/search`）返回 `code=2004`，不对外开放，所以事件归并是自己做的。
- iFinD 的检索每次都会返回内容，哪怕不相关；同一个检索词连续调用两次，返回的新闻不完全相同。所以每条内容都要先判断相关性，刷新时可能取到之前没见过的报道。
- iFinD 把同一份公告切成多个片段返回，而且每次只返回其中几段。程序按标题和日期合并，多次取到的片段累加。
- iFinD 给的公告日期可能和实际发布差一天：光迅科技的澄清公告日期是 11 月 4 日，多家媒体写的是“11 月 3 日晚间发布”。页面把几种说法并排列出，不判定哪个准确。
- 两个数据源都没有“传闻”标签，传闻的原帖也经常取不到。

“示例自选股”是一份构造的示例名单，不是任何真实用户的持仓。取回的原始数据、事件文件、AI 缓存都在数据目录里，不进本仓库。

## 六、已知边界

- **“最早来源”只是我们取到的最早一条**，不保证是这件事真正的源头。传闻原帖取不到时，页面写“原始出处未取到”，不给它编一个日期。
- **只有日期时分不清先后。** 同一天、缺时分、原文又没有互相指向的证据，并列显示并标“先后未明”。
- **数据源只给片段，条数有上限。** 关键的那句话如果不在取回的内容里，产品看不到。页面顶部会标“结果可能被条数上限截断”。
- **AI 的判断会出错，而且同一段原文两次判断可能不同。** 关系、态度、是不是同一件事、哪些是转载，都是 AI 判的。三个真实示例的逐条核对结果和不一致的条目见《测试说明》。
- **给 AI 的每段原文只取前 6000 个字。** 更长的公告，后面的内容 AI 读不到。
- **一件事只给一个结论。** 更正公告点名了更正对象时，只让被点名的那份失效；没点名时，规则会把同一来源此前的说法整体标成“已被更正”。公司回应里部分确认、部分否认时，如实显示成“正式回应部分确认部分否认”并分项列出。
- **“办理阶段”只认固定措辞。** 措辞不在规则里的公告认不出阶段，这时页面不显示这一项，说明句退回“已正式确认此事”。规则不核对“董事会通过的”和“待股东会审议的”是不是同一项议案：一份公告里董事会通过的是别的议案、待股东会审议的是这件事时，会被标成“董事会已审议通过，尚需提交股东会审议”。状态名没有为“只是提议”单设一个，仍显示“已获正式确认”（公司确实正式公告了收到提议），下面用“办理阶段”一行说明。
- **“办理阶段”在真实公告上验过的范围。** 除三个示例和中际旭创外，另从 iFinD 取了 50 份回购、重组类公告：认出 31 份（只是提议 10、尚在筹划 9、董事会已通过且无需股东会审议 12），逐份复核没有标错；19 份没有阶段措辞，不标。“须经……后方可实施”“通过的是终止类议案”“股东会决议未通过”这三种情形在这 50 份里没有出现，只用构造的句子测过。综合稿规则的两个数（3 家、2 次）是看三个示例的数据定的。
- **同一家媒体先后采访了不同的人、说法相反时，会被当成这家媒体改了口**，旧报道标“同一来源后来改了说法”。媒体声明“以本次更新为准”但态度没变时，新旧两篇都算有效。
- **事件脉络里，“仅见网络说法”变成“已有署名媒体报道”这一步仍标“结论未变”**：状态都是“待证实”，那一步自己的说明句会显示新说法。
- **来源名单是自己拟的**（28 家财经媒体算“中”，名单外一律算“低”），页面上可以查看。30 天的过期期限也是自己定的假设值，没有找到可引用的行业标准。
- **事件脉络是按发布时间推演的**，不是我们当天实际记录下来的。
- **过期判断依赖及时复查。** 数据来源超过 24 小时没成功复查、或结果被截断时，不判“已过期”，只写“在已取回的结果中未见后续”。示例事件的数据是提前取的，过了 24 小时页面会提示并提供刷新。
- **现场查询有次数上限**（默认每天 10 次，线上 50 次），因为 iFinD 试用账号总共只有 2,000 次调用，每查一件事用 2 次。用完当天额度后示例仍可查看。
- **线上地址没有自己的域名。** 主地址借用了免费的域名解析服务 sslip.io（`43-172-79-197.sslip.io` 会解析到服务器的 IP），证书 90 天有效；备用地址直接用 IP，证书是 Let's Encrypt 的短期证书，约 6 天一续，靠服务器自动续期。最初上线时只有 `http://` 加 IP，浏览器会先弹“此网站不支持安全连接”的警告，所以补了 HTTPS；旧的 `http://43.172.79.197/` 现在会跳转到主地址。服务器在腾讯云硅谷机房，2026-11-20 用公开拨测服务从中国大陆电信、移动、联通共 15 个测试点访问主地址全部成功、证书受信任，但评审所在网络的情况没法事先确认。
- 数据源偶尔连接失败。失败自动重试一次，仍失败则页面顶部写明哪个来源失败；公告检索失败时不给结论。

## 七、未做事项

| 没做 | 原因 |
|---|---|
| 自动发现全市场的新事件、推送提醒 | 24 小时内做不扎实；试用额度也不够 |
| 定时自动更新 | 改为用户手动刷新 |
| 一个事件拆成多个说法分别给结论 | 做不扎实，见“已知边界” |
| 分析事件对股价的影响 | 容易变成涨跌判断，题目规则禁止 |
| 用户登录、真实持仓、关注名单的增删 | 规则要求用构造数据；时间留给主链路 |
| 展示公告和新闻全文 | 数据源只给片段 |
| 用扶摇的公告详情接口补全公告正文 | 公告编号能不能对上没有验证 |
| 多人同时使用时的任务排队、数据库 | 事件存成 JSON 文件，后台任务在内存里；单实例够演示用 |
